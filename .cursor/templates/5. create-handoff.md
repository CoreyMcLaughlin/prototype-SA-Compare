# Rule: Creating a Handoff Document

## Goal

Turn a prototype into a short handoff document that product can review to write user stories. It captures what the prototype does, how the prototype differs from the real product, the user paths it covers, and the edge cases worth thinking about. It is product-first, with just enough engineering context to be useful.

The handoff is for product to write stories from what exists now, not from the original plan. This document is not a second PRD. Keep it short. Do not restate or mirror the PRD or task list. If it starts to read like a PRD, cut it.

## Sources of truth (in order)

1. **What was actually built:** the prototype code and how it behaves.
2. **Prior chat / Cursor session decisions:** deviations, stubs, naming calls, test intent.
3. **PRD and task list:** light backup only, to fill gaps or link. Do not restate or mirror them.

## When to run this

Run this flow when the user says anything like:

- "Create the handoff documentation"
- "Update the handoff documentation"
- "Write the handoff doc"

It is also offered at the end of the prototype workflow (Step 7 wrap-up in `prototype-workflow.mdc`). It is available on demand after a prototype exists. A missing PRD or task list is fine (concept path).

## Process

1. **Read the prototype first.** Read the prototype code and how it behaves, plus the prior chat / session decisions. This is what the handoff documents. Skim the PRD in `.cursor/documents/prds/` and task list in `.cursor/documents/tasks/` only to fill gaps or link them. A missing PRD or task list is fine.
2. **Pick the prototype.** If more than one PRD exists, ask the user which one(s) the handoff is for.
3. **Check for an existing handoff.** Look in `.cursor/documents/handoffs/` for a file matching the PRD. If one exists, offer to update it in place rather than creating a duplicate.
4. **Draft from the build.** Fill each section from what the prototype does now. Prefer "what users can do in the build" over copying PRD user stories or requirements.
5. **Gather the links a reviewer needs.** Put the deployed link (with `?pw=` if it exists), the local entry file, the Figma frames, the PRD, and the task list in the header. If a task list exists, use its unchecked items to fill the "Not built" rows and the Status line, so what is left is visible near the top.
6. **Keep build status in one place.** Record what is built, partial, and not built in the "What's built" table. Do not repeat that status in every other section; reference the table instead.
7. **Ask only for what is missing.** Do not re-ask things already clear from the build or chat. The most likely gaps are:
   - The learning goal, if it was never written down.
   - How you will know it worked (the success signals), if that was never discussed.
   - Prototype vs product notes, if that difference was never discussed.
   - The deployed link and password, if there is one and you do not have it.
   Ask these in one message, only for the fields you cannot fill yourself.
8. **Write the file.** Use the template below.
9. **Save it.** Save to `.cursor/documents/handoffs/` using the naming convention below.
10. **Confirm and offer follow-ups.** Tell the user where it was saved and ask them to review it. If the PRD looks stale against the build, offer to update it. Do not edit the PRD or any other doc unprompted.

## Output

- **Format:** Markdown (`.md`)
- **Location:** `.cursor/documents/handoffs/`
- **Filename:** `handoff-[prd-file-name].md`, matching the base name of the PRD (e.g. PRD `0001-prd-coach-booking.md` produces `handoff-0001-prd-coach-booking.md`).

## Writing style

- Write for a product manager, not a developer.
- Use really simple, everyday language. A non-technical reader should understand every line.
- Be direct. Short sentences. No filler.
- No technical jargon or developer shorthand. Describe what the user sees and does, not how it is built.
  - Instead of "not exercised in UI", write "you cannot do this in the prototype yet".
  - Instead of "tab-local", write "only saved on this tab".
  - Instead of "Hash deep-links...", write "links that jump straight to a screen".
  - If a technical term is unavoidable, explain it in plain words the first time.
- Do not use em dashes.
- Do not use words like leverage, robust, seamless, streamline, or elevate.
- Use realistic values and real feature names, not placeholders.
- If a section has nothing to report, write "None" rather than padding it.

## Template

```markdown
# Handoff: [Prototype Name]

**Status:** [build state in one line, e.g. Partial build: Overview and Payouts ready; Disputes and Invoices not built]
**Prototype:** [deployed password-protected link if there is one, e.g. https://[url]?pw=... , plus the local entry file, e.g. finance.html]
**Figma:** [link to the authoritative frames, if any]
**PRD:** [link to the PRD file, if one exists]
**Task list:** [link to the task list file, if one exists]
**Date:** [YYYY-MM-DD]

## Learning goal

The one thing this prototype was built to test. One or two sentences.

## How we will know it worked

What success looks like for the learning goal, and what to watch for when testing with users. Tie each signal back to the goal. Keep it to a few plain lines.

- [signal, e.g. a venue owner can find and explain their last payout without help]
- [signal, e.g. users stop asking support "where is my money"]

## What's built

One place for build status, so the rest of the doc does not repeat it. Reference this table from the sections below instead of restating what is or is not built.

| Area | Status | Notes |
|---|---|---|
| [area, e.g. Overview] | Built / Partial / Not built | [one plain line] |

## Main user stories

What users can actually do in the build. Derive these from the prototype, not the PRD. Write each as:

- As a [user], I want [action], so that [outcome].

## Prototype vs product

What the prototype does versus what the real product should do. Only include points that were discussed or are clear from the build. Use a two-column list:

- **Prototype:** [what it does now] → **Product:** [what the real thing should do]

If this was never discussed, write "Not discussed."

## User paths

The paths a user can take through the prototype. List the happy path first, then any variations.

1. [Path name]: step, step, step.
2. [Path name]: step, step, step.

## Edge cases

Real situations a user could hit, written from their point of view, and what they see when it happens. Say whether the prototype handles it or not. Avoid developer notes; describe the user's experience.

- When [situation the user runs into], the user sees [what happens]. [Handled / not handled / open question.]

## In / out of scope

What the prototype deliberately included and skipped, so product does not assume skipped items are done.

- **In scope:** [list]
- **Out of scope:** [list, e.g. auth, error states, real data]

## Open questions and assumptions

Decisions made during the build that are not in the PRD, and anything still unresolved.

- [Question or assumption]
```

## Final instructions

1. Do not start changing the prototype. This step only writes documentation.
2. Fill everything you can from the build and prior chat before asking the user anything.
3. Keep it short and product-focused.
4. After saving, ask the user to review it.
